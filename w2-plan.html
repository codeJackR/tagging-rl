Warning one — the reward-weights file says usable: false

Only 78 of 4,500 eval cells were reviewed by a human, so no attribute cleared the evidence bar and every reward_weight came out 0.0.

A reward function that reads that file literally scores nothing at all — and it fails silently, because zero reward is indistinguishable from a model that never gets anything right. Check the flag first, fall back to uniform weights.
rel = json.load(open("data/reliability.json"))
weights = rel["reward_weights"] if rel["usable"] else {}   # uniform fallback

Warning two — quote deltas, never absolutes

Gold equals the frontier's own answer on 98.3% of cells, which is why the ceiling run reads 0.9915. That number is close to tautological.

SFT vs GRPO against identical gold is a real comparison — the delta is meaningful. "We reached 99% of frontier quality" is not a claim this eval set can support.

While it trains, fill the difficulty column

Every row carries difficulty.sft_pass_rate, currently null on all 3,600. Sample k=8 completions per row from the SFT checkpoint and record the fraction correct.

GRPO's gradient comes from disagreement within a group of rollouts. A row every rollout gets right — or every rollout gets wrong — contributes nothing but compute. Keeping 0 < pass_rate < 1 is the single cheapest speedup available, and it can only be measured once a baseline model exists.

2 · Write the reward as a plain function over the verifier

one import path, two callers — the architecture claim
→

TRL takes reward functions directly — several at once, with weights, and it skips None returns for samples a reward doesn't apply to. Start with three:

rewardreadsexpect
format validityresult.schema_validrises fast, then saturates
vocab + rule compliancevocab_valid, rule_violationsrises, then saturates
golden agreementper-attribute vs goldthe one that keeps giving
# the same module the tests import — that IS the claim
from verifier import load_pack, verify

def reward_format(completions, **kw):
    return [1.0 if verify(c, PACK).schema_valid else 0.0 for c in completions]
done when → the same verifier module is imported by reward and tests
↳

Plan the reward ladder now, not at step 80

A validity reward hits its ceiling and stops contributing gradient entirely — in the earlier smoke test that happened around step 80. If nothing graded sits underneath it, training goes flat and looks broken when it's merely finished learning the easy part.

Put per-attribute partial credit underneath from the start, ideally rarity-weighted. Validity is the floor, not the objective.

No structured decoding here — that's the whole point

Constrained decoding would make schema-valid JSON free, which deletes the exact reward signal you're trying to study. Let the model emit garbage and watch it learn not to.

The labelling run in week 1 had structured outputs on, because there you just wanted clean data. Here you want to watch the model fail. Same schema, opposite setting, and the difference is the point.

4 · Shape, re-run, compare

stop at a clean story, not a maximal number
→

Three shaping moves, in order of expected payoff:

Per-attribute partial credit — binary all-or-nothing gives dead gradients on 15-field records.
Class-balanced weighting — otherwise rare values are never worth learning.
Validity as a gate, not a reward — invalid output scores zero rather than earning partial credit for being well-formed nonsense.

Each iteration is one tracked run with a delta against SFT. Resist tuning until the number is maximal; stop when the story is clean.

done when → GRPO beats SFT on macro-F1, or you can explain why it doesn't
"Or you can explain why it doesn't" is a real pass condition. A well-understood negative result is a better artifact than an unexplained positive one, and far harder to fake.

Length budget that looks like a broken reward

A completion budget set too low clips the output mid-JSON, so the format reward becomes structurally unreachable — the model literally cannot emit a closing brace. It presents as a broken reward function.

Measured on the training corpus: prompt p95 ≈ 248, target p99 ≈ 94. But that's the chars/4 heuristic — re-measure with the Qwen tokenizer before setting the config, because a heuristic mistaken for a measurement is how this happens twice.

uv run python scripts/build_dataset.py plan \
  --labeled data/raw/labeled.jsonl --tokenizer Qwen/Qwen2.5-0.5B-Instruct
2

Zero gradient from rows that are too easy or too hard

In the smoke test, half the steps showed grad_norm ≈ 2e-05 — all eight completions scored identically, so there was nothing to learn from. An obvious crew-neck cotton tee will be solved by every rollout.

This is why sft_pass_rate exists. Fill it after step 1, then filter to 0 < pass_rate < 1. It cannot be guessed from the data — only measured against a model.
3

GRPO eats far less data than you'd expect

With per_device_train_batch_size=8, num_generations=8, grad_accum=1, TRL consumes one unique prompt per optimizer step. A 300-step run touches ~300 prompts.

The 3,600 rows exist for the SFT baseline and to leave filtering headroom after difficulty scoring — not because GRPO will consume them. Quality and difficulty spread beat raw count.

4

Eight fields cannot be measured, and the README should say so

fieldlabelledfieldlabelled
sleeve_style2%neckline20%
waistline2%closure24%
silhouette7%pattern25%
garment_length11%fit29%

Gold unknown is unscorable — there's no ground truth to compare against. At 2% labelled, sleeve_style contributes about six usable cells to the whole eval set, and its F1 term is noise.

A reader will otherwise assume all 15 fields were measured equally. One line in the README is the difference between an honest result and an overstated one.
5

Don't diagnose a broken reward at step 50

Unsloth's own guide notes that GRPO runs often need 300–1000+ steps before anything visibly moves. Flat early curves are the normal case, not evidence of a bug.

The order is the argument. The baseline comes first because it's the only thing that makes the second number mean anything; the reward is written over the verifier because a reward and a test that disagree are two different specifications of correctness; decoding stays unconstrained because a model that can't fail can't be observed learning not to.
