Which is why guessing token counts kept failing

Three different estimates of the same labelling prompt, before anyone measured:

methodsaidtruth
characters ÷ 47461,908
tiktoken o200k_base805
the API's own count1,908

Both shortcuts were wrong by more than 2×, in the same direction. Vocabulary lists tokenize badly — they're dense with rare words and underscores.

Our snake_case values cost 3 tokens where a plain word costs 1. Not worth changing now — renaming values would invalidate 20,000 paid-for labels — but worth knowing the target JSON is roughly twice as long as it needs to be.

Why the budget matters

Two limits, two different failures

both have already cost someone a day
1

max_completion_length — set it too low and the reward becomes impossible

The model writes until it hits the limit, then stops mid-character. Not "a shorter answer" — a broken one:

{"closure": "unknown", "collar_type": "unknown", "colour_prim◀ cut
That isn't valid JSON, so the "did you produce valid JSON?" reward can never be earned. The score stays at zero no matter how well the model learns — and it looks exactly like a broken reward function. In an earlier run this clipped 50–87% of outputs and cost a day of debugging.

It already bit us once this week, on the Gemini adjudication run: 20% of rows returned truncated JSON, which surfaced as a parsing error rather than a budget one.

170 against a 118-token maximum. Zero risk, and the wasted memory is negligible.
2

max_prompt_length — set it too low and you silently delete evidence

Over-long prompts get cut from one end. No error, no warning — the model simply never sees the last part of the description.

Marking an exam where the last paragraph of the question was torn off. The student's answer looks wrong; the paper was the problem.

And it's not random which ones get cut — the longest descriptions are the most informative ones. You'd be blinding the model precisely where the text had the most to say.

324 still clips 55 rows (1.5%). Raising it to ~600 covers everything at some memory cost.

Worth deciding rather than defaulting: 1.5% of rows lose their tail, and they're disproportionately the rich ones. Cheap to fix now, invisible later.
3

Why not just set both enormous?

Memory scales with the limits, whether or not the text is that long. A larger budget means smaller batches, or no room on the GPU at all.

The point of measuring is to pick the smallest number that clips nothing — not to guess a round one and hope.

The numbers to put in the config

Settled

measured with the real tokenizer, on the real training set
▸
max_prompt_length     = 324   # p95 + 15% — clips 55/3600 (1.5%)
                        600     # clips nothing, costs memory
max_completion_length = 170   # p99 + 20% — clips 0/3600
                        335     # if you add a reasoning block

The 335 figure matters if you later ask the model to think before answering — reasoning tokens are charged against the same completion budget. That's exactly what broke the Gemini run: ~1,000 thinking tokens against a 2,048 limit left too little for the JSON.

Both numbers exist to answer one question: is the model failing, or was it never given room to succeed? A clipped completion and a broken reward function look identical from the outside — the only difference is that one is fixed by a config line and the other by a week of debugging. Measuring first is what keeps you from confusing them.
